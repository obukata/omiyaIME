# 開発とリリースの進め方

2026-11-27 に利用者と決めた運用。機能ごとに並行して進められるようにし、`main` は常に「このMacに入れて普段使いできる状態」に保つ。

## ブランチ

| ブランチ | 役割 |
|---|---|
| `main` | リリース済みの状態だけを置く。直接コミットしない（文書の小さな修正は例外として可）。 |
| `feature/<名前>` | 機能ごとの作業ブランチ。例: `feature/omiya-walk`（おみや君の散歩）、`feature/learning`（学習機能）。 |
| `fix/<名前>` | 不具合の修正。例: `fix/duplicate-input-source`。 |

- ブランチは `main` から作る。並行して進める機能は、別々のブランチで進める。
- 仕様の検討や調査だけの段階でも、ブランチ上で文書（`docs/`）を更新してよい。
- 長く続くブランチは、ときどき `main` を取り込んで差を小さく保つ。

## 試用（ブランチの版をこのMacで試す）

インストール先は `~/Library/Input Methods/omiyaIME.app` の1か所だけなので、ブランチの版を試すと、普段使いの版も置き換わる。

1. ブランチでビルドしてテストする（`README.md` の「ビルドとテスト」）。
2. `./Scripts/install.sh` で入れて、普段どおり使って確かめる。
3. 問題があれば `main` に戻ってビルドし直し、`./Scripts/install.sh` で元の版に戻す。

## リリース

1. 作業ブランチで、テストがすべて通り、利用者が実機で確認していることを確かめる。
2. `Bundle/Info.plist` の版を上げる。
   - `CFBundleShortVersionString`: 見える版番号。機能追加で `0.x.0`、修正だけなら `0.x.y`。
   - `CFBundleVersion`: ビルド番号。リリースごとに1つ以上増やす。
3. `CHANGELOG.md` に、利用者向けの言葉で変更点を書く。
4. `main` へマージする（GitHubのプルリクエスト経由）。
5. `main` に `v0.x.y` のタグを付けて push する。
6. `main` をビルドして `./Scripts/install.sh` でこのMacに入れる。これが「本番」。

GitHubの「Release」ページの作成や、ほかの人への配布は、利用者が明示したときだけ行う（AGENTS.md）。
